The chain, in five lines

  1. A workflow owns ordered rungs — Red, Yellow, Green.
  2. An asset type points at one workflow. That pointer is the entire reason an asset shows a ladder.
  3. The type maps task templates onto each rung.
  4. Every asset of that type gets one task instance per mapped template.
  5. Answering a task opens a run; the run clears the rung; the rungs are the tag.

Where the sheets do not register

  • task_item appears under three different api-v2 tables — the question, its placement, and the section header. One table has to become three.
  • asset_type.workflow_id is nullable for us and NOT NULL for them. Seven dev rows are null, so today's data would fail the migration, not just hide a ladder.
  • Our per-item note maps onto a comment that belongs to the whole run, so the item is lost.
  • A question is reusable across tasks for them and owned by one version for us — which is why we snapshot the wording and they do not need to.
  • The 3D element link is ours alone. Sign-off does have a home there — as a checklist item, not a table — but our role, party and drawn image do not.

Which database am I on?

  • dev — local and dev builds, fed by the develop branch of xyz-supabase.
  • stable — staging, preprod, prod, fed by main. Level with dev since 4 Sep; it had been five weeks behind, which is what the staging 400s were.
  • Picked at runtime from the Spring profile, not at build time.
  • Row-level security is permissive throughout — separation is client-side only.
